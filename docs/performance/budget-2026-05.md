## 1. Route bundle budgets (First Load JS, gzipped)

| Route group | Path(s) | Budget | Why this number |
| --- | --- | --- | --- |
| Marketing | `/`, future `apps/web/app/(marketing)/**` | **≤ 90 kB** | Plan north star is conversion. Sub-90 kB is what keeps LCP < 1.5s on a throttled Moto G4 over Fast 3G. Hero must remain pure CSS / RSC; `motion` and `gsap/ScrollTrigger` are dynamic-imported below the fold. |
| Owner intake | `/o/intake/**` | ≤ 110 kB | Owners arrive over cellular from a WhatsApp deep-link. No JS animation libraries (motion-system §2). Budget includes Supabase client + Zod. |
| Clinic app baseline | `/inbox`, `/customers`, `/pets`, `/directory`, `/settings`, `/reminders`, `/reports`, `/requests/**` | ≤ 130 kB | Authenticated staff on broadband; richer interactivity (DnD-kit, Radix, realtime). CSS-only motion per motion-system §2. |
| Admin | `/admin/**` | ≤ 160 kB | Low-traffic, internal users on broadband. Treated as a soft cap, not a release gate. |

These are **per-route** budgets, not total app size. They measure the "First Load JS" column from the `next build` output: the bytes a cold visitor downloads before any interaction.

## 3. How `/_vitals` works

```
                 production-only
  page hydration ────────────────► <WebVitalsReporter />
                                        │
                                        │ useEffect(() => import("@/lib/web-vitals"))
                                        ▼
                              registerWebVitals()
                                        │
                                        │ onLCP / onINP / onCLS / onFCP / onTTFB
                                        ▼
                              navigator.sendBeacon("/_vitals", payload)
                                        │ (fetch + keepalive fallback)
                                        ▼
                       apps/web/app/_vitals/route.ts (Node runtime)
                                        │
                                        ▼
                          console.log({ kind: "web-vitals", ... })
                                        │
                                        ▼
                              Vercel function logs
```

**Reading the data today.** Until a Sentry/PostHog sink lands, samples are
visible in:
- Vercel Dashboard → Project → Logs, filter by `"kind":"web-vitals"`.
- `vercel logs <deployment-url>` from the CLI.

**Reading the data after the follow-up.** The route handler will fan-out
the same validated payload to PostHog EU (`capture` event `$web_vitals`)
and Sentry performance (custom measurement on the active transaction).
That work is intentionally out of scope for this PR — it requires new
env vars and a contract in `docs/contracts/` for the PostHog property
naming. Open a follow-up under `claude/ui-vitals-sink-<date>`.

**Production gating.** `WebVitalsReporter` is a no-op when
`process.env.NODE_ENV !== "production"`. Dev work never reaches the
endpoint, and Lighthouse runs against `next build && next start` will
fire the reporter — keep that in mind when reading the dev console.

**Beacon transport.** `navigator.sendBeacon()` is preferred because it
survives `pagehide`, which is where INP and CLS commonly finalise. The
`fetch` fallback uses `keepalive: true` to mirror that lifetime.

**Where the reporter is mounted.** This PR ships the component but does
not wire it into the marketing layout — `apps/web/app/(marketing)/layout.tsx`
is owned by Wave 2a (`frontend-engineer` landing motion build). The
follow-up there must add:

```tsx
import { WebVitalsReporter } from "@/app/_components/WebVitalsReporter";
// ...
<body>
  {children}
  <WebVitalsReporter />
</body>
```

at the bottom of the marketing `<body>`. The reporter is idempotent if
mounted in multiple layouts.

## 4. "Do not add to the landing" list

These categories are budget-busters at the LCP frame and have no
narrative justification in the plan. If a future change wants to add
any of these, it requires a written waiver in `docs/contracts/` and a
fresh measurement against this budget.

- **Lottie** — pulls a runtime + JSON parse + canvas/svg renderer; the
  motion-system explicitly rejects it.
- **three.js / WebGL hero scenes** — ~150 kB gz floor, GPU contention
  with View Transitions.
- **GSAP plugins beyond `ScrollTrigger`** — `Flip`, `MotionPath`,
  `Draggable`, `MorphSVG`, etc. Motion-system §6 names this constraint.
- **Autoplay video heroes** — main-thread decode on first paint, kills
  LCP on cellular. Use a static poster + lazy load if a video is
  genuinely necessary.
- **Audio** — there is no narrative justification on a B2B SaaS marketing
  page; accessibility tax is high.
- **More than one web font weight per family** — Montserrat 400/500/600/700
  and JetBrains Mono 400/500/600 are already loaded in `app/layout.tsx`.
  Adding new families or weights requires a measurement-backed waiver.
- **Client-side analytics or A/B testing scripts loaded in the critical
  path** — defer with `next/script strategy="lazyOnload"`.
- **Iframes above the fold** — embedded calendars, chat widgets, social
  embeds. They block LCP and confuse CLS.

## 5. Configured optimizations

`apps/web/next.config.ts`:

- `experimental.optimizePackageImports: ["lucide-react", "motion"]` — barrel
  tree-shaking so named imports do not drag the full module index into a
  route bundle. `gsap` is intentionally not included; see the inline
  comment in `next.config.ts` for the rationale.
- `experimental.viewTransition: true` — already enabled; cross-route
  morphs use the leitmotif curve per motion-system §4.

Fonts are loaded via `next/font` in `apps/web/app/layout.tsx` with
`display: "swap"` for zero-CLS rendering. No `<link>` Google Fonts tags
exist anywhere in the tree.

## 6. Verification workflow

Manual today, CI follow-up later:

1. `npm run build` from the repo root. Inspect the per-route "First Load JS"
   column in the Next.js output.
2. For the marketing route specifically, ensure `motion` and `gsap` appear
   only in the dynamic chunks (the Wave 2a brief mandates dynamic import
   below the fold).
3. Run Lighthouse mobile against `next start` over a throttled Moto G4
   profile. Capture LCP / INP / CLS to compare against §2 thresholds.
4. Once the PostHog/Sentry sink lands, validate samples in production by
   triggering a real navigation and grepping the Vercel logs for
   `"kind":"web-vitals"`.

A bundle-size assertion script (`apps/web/scripts/check-bundle.ts`,
already wired into `npm run check:bundle`) is the natural home for a CI
gate against the §1 budgets. Wiring it to the budget table is a Wave 3
task and is intentionally not done here.
